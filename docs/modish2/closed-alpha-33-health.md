# 3.3 — liveness, readiness и честная проверка клиента

Локальный срез 19 октября 2026. Без production deployment.

- `/health/live` сообщает, что процесс отвечает. Он не создаёт Session,
  не обращается к БД и не зависит от белого списка участников.
- `/health/ready` выполняет проверку БД: `200` с `status=ok, database=ok`
  при успехе; `503` с безопасным `degraded/error` при ошибке создания сессии,
  получения соединения, запроса или освобождения ресурсов.
- `/health` сохраняет старые HTTP200 и поля status/database/version для
  совместимости существующих проверок. При сбое его status остаётся degraded,
  что новый Flutter больше не принимает за готовность.

Проверка БД полностью находится внутри защищённого участка, включая создание
и закрытие сессии. Используется текущий `get_db` и его явная тестовая подмена;
неподдерживаемая/сломанная подмена не приводит к запасному подключению рабочей БД.
Диагностика подключения, адреса, токены и исключения не выдаются в health JSON.

Новые probe-пути исключены из общего rate limit точным совпадением URL.
Прочие URL с префиксом `/health` не получают исключения. Прежние исключения
документации API сохранены.

Flutter проверяет readiness перед входом/регистрацией: нужны одновременно
HTTP200, status=ok и database=ok. Только404 нового endpoint разрешает один
переход на старый `/health` с такими же строгими критериями. Degraded,503,
неизвестное тело и сетевой сбой не вызывают запасной успешной проверки.
Probe не должен обновлять токен/запускать общий повтор запроса.

## Границы

Readiness здесь означает доступность процесса и проверяемой БД. Она не
подтверждает полноту миграций, покрытие каталога размерами, наличие вещей
в checkout или доступность необязательного внешнего фото-провайдера.
Клиентский запрос ограничен таймаутом; глобальные настройки таймаутов DB engine
не менялись и отдельный жёсткий серверный deadline подключения не заявляется.

Все три health-ответа имеют `Cache-Control: no-store`.
