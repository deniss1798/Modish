# 3.2 — белый список закрытой альфы

Локальный срез 18–19 октября 2026. Выбран белый список email: ТЗ допускает его
вместо инвайт-кодов. Новые поля регистрации, таблицы и зависимости не нужны.

## Настройка

- `CLOSED_ALPHA_ENABLED=false` — прежний режим по умолчанию.
- `CLOSED_ALPHA_ENABLED=true` — допускаются только адреса из
  `CLOSED_ALPHA_ALLOWED_EMAILS`, разделённые запятыми; максимум50.
- Пустой или неверный список, неизвестное/пустое значение флага при его
  явном задании запрещают доступ. `true/false/1/0` — допустимые значения флага.

Адреса проверяются существующим EmailStr. Только сравнение политики убирает
внешние пробелы и регистр. Аккаунты не переименовываются; точки и `+` не
склеиваются, доменные маски не расширяют допуск. Значения списка не попадают
в ошибки или логи. Белый список ограничивает указанный email; он не является
проверкой владения почтовым ящиком и не добавляет email verification.

## Границы доступа

Проверка действует при регистрации до записи/хеширования пароля, после
проверки пароля при входе, при выдаче/обновлении сессии и в общей проверке JWT.
Старый access/refresh token не обходит удаление адреса из текущей политики.
Прежние пользователи также должны быть явно включены в список.
Публичные list/detail/brands маршруты каталога требуют допуска, если альфа
включена; при выключенной альфе их прежний контракт сохраняется.
Выход остаётся доступным, чтобы можно было отозвать сессию.

Настройки перечитываются из environment текущего процесса при проверке.
Это не наблюдение за `.env` или переменными родительского процесса: обычное
изменение серверной конфигурации требует её применения/перезапуска процесса.

Клиент распознаёт только точное безопасное сообщение о закрытом тестировании,
включая отказ refresh. Неизвестный текст403 остаётся скрытым; ошибка доступа
не выдаётся за исчерпанную квоту фото или истёкший пароль.

Рабочая конфигурация не менялась, реальные участники не добавлялись, приглашения
не рассылались. В примере конфигурации режим выключен и список пуст.
