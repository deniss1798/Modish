## Данные и правила

`build_product_dna(product)` создаёт воспроизводимый JSON без сети и изменения модели. В снимке отдельно хранятся commerce-поля и семантические признаки. Цена, размер, наличие и дата наблюдения копируются с пометкой `model_snapshot_unverified`; словарь не подтверждает эти факты и не ослабляет Quality Gate.

Небольшой словарь `fashion_taxonomy_v1` содержит 6 измерений: стиль, цвет, материал, сезон, посадка, силуэт. Это не полная taxonomy на 50–80 атрибутов из плана. Версии схемы и правил — `product_dna_v1` и `product_dna_rules_v1`. Общая версия нормализации — `catalog_rules_v4`; прежний словарь категорий сохраняет собственную версию `category_core_v1`.

Каждое утверждение содержит каноническое значение, правило, источник, исходное поле и текст. Уровни 0.95 для структурированного поля, 0.80 для названия продаваемой вещи и 0.35 для прежнего поля модели — оценки надёжности правил, а не измеренные вероятности. Legacy-поля не выдаются за подтверждение магазина. Несогласованные свидетельства остаются конфликтом.

Название обрезается до рекомендаций и частей после «с/со/для/к/под»; описание не используется. Шёлк из «рубашка с шёлковым шарфом» не становится составом рубашки. Отрицания и нулевой процент материала сохраняются как блокирующее свидетельство: положительное слово из другого поля не перекрывает «без шерсти». При неоднозначной области отрицания всё измерение остаётся неизвестным. Это намеренно консервативные правила; они могут пропускать часть корректных признаков.

## Подключение

Импорт и replay сохраняют DNA внутри `CatalogRecord.canonical_json.product_dna`. Новая миграция для него не нужна. Raw-запись, идентификаторы товара и время наблюдения наличия сохраняются при повторной обработке.

В User Twin и MIE подключены только подтверждённые материал, посадка и силуэт. Например, «100% хлопок» становится значением `cotton`. Ключ обучения имеет префикс `product_dna_rules_v1:`: старые неподтверждённые оценки остаются в БД, но не передают новой версии свою уверенность. Стиль и цвет пользователя не сбрасываются. Обработчик событий и MIE используют одинаковые ключи; интеграционный тест подтверждает, что реальный like создаёт предпочтение материала и меняет его вклад в оценку.

Основная female-first лента пока ранжируется по прежним style/category/color/brand. Индекс поиска кандидатов по DNA, влияние материала на эту ленту, смена style/color, image enrichment и новый Context Engine в этот блок не входят. Нельзя заявлять рост пользовательских метрик или улучшение всей выдачи по материалам на основании этих тестов.

## Исправление аналитики

- `reached_card10_rate` считается среди пользователей, начавших ленту; добавлены `started_feed_users` и отдельный `onboarding_to_card10_rate` для всех завершивших онбординг.
- Поздние сохранения, открытия и переходы по первым 20 вещам сохраняются после вытеснения их ID из текущего списка выдачи. Повторные события не увеличивают число уникальных показов; Style Swipe исключён.
- После сетевого сбоя показ видимой карточки можно отправить повторно. Одновременные и успешно записанные просмотры не дублируются.
- Запрос партнёрской ссылки сохраняется как raw intent, но не означает подтверждённый переход. Клиент отправляет событие после успешного открытия внешнего приложения; это также используется для «Купить всё». Ошибка запуска не увеличивает счётчик открытых ссылок. Успешный запуск не доказывает загрузку страницы продавца или покупку; сбой отправки аналитики после запуска может недосчитать переход.
- В данных выдачи сохраняется фактическая версия ранжировщика. Старый `/analytics/summary` сохраняет совместимые ключи и явно подписывает CTR как отношение запросов URL к доставленным API карточкам, включая prefetch. Для первых 20 показов используется `/analytics/first-session`.

Назначение экспериментальных групп, baseline и статистически достаточный пользовательский эксперимент ещё не запущены. [Протокол](feedback_benchmark_protocol.md) и [синтетический replay](activation-feedback-replay.json) описывают отдельные задачи.
