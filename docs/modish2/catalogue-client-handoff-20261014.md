# Отдельный каталог магазинов: клиентский контракт и проверки

14 октября 2026. Клиент проверен локально с fake API и in-memory HTTP adapter. Эта проверка не выполняла real HTTP, сборку APK, публикацию или обновление сервера. Финальный общий прогон и визуальные снимки выполняет владелец release.

## Граница продукта

`DiscoveryScreen` — отдельный просмотр каталога, а не ослабленный вариант персональной ленты. У него есть входы из профиля и поиска, включая пустой результат поиска с сохранением исходного запроса. Входы появляются только при capability `catalogue_discovery_v1`; число основных вкладок остаётся равным четырём. Дополнительные входы из пустой ленты и Style Swipe интегрирует root.

Экран читает только `GET /catalog/discovery`. Ответ обязан содержать `mode=catalogue_discovery`, `personalized=false`, `size_verification=not_verified`. Каждый товар также обязан иметь discovery metadata. Несоответствующий ответ не показывается как проверенный персональный товар. Все остальные admission правила, включая допустимые магазины, бюджет, пол, реальную доступность, ссылку и качество фотографии, остаются на сервере.

`Product` хранит дополнительные immutable merchant-size записи отдельно от snapshot, который поддерживает причины строгих рекомендаций. UNKNOWN не превращается в EU/RU по виду числа. Пользователь видит исходную подпись магазина, явно указанную систему и доступность; неизвестное наличие отмечено как требующее уточнения. Предупреждение «Размер нужно уточнить у магазина» сохраняется и в списке, и в detail.

Режим detail сохраняется по origin metadata. Обновление использует `GET /catalog/discovery/{id}`, который сервер повторно проверяет по всем правилам кроме exact fit. При отказе чтения прежнее предложение не допускает переход в магазин до успешной проверки. Discovery не вызывает strict complements, не показывает персональные причины и Like/Save. Primary action — «Открыть магазин».

В этом режиме чтение, открытие detail и переход в магазин не отправляют `/recommendations/events`. Merchant link использует существующий `/affiliate/click` для получения проверенной URL и ledger, но optional `recordRecommendationEvent=false` отключает подтверждение, которое прежний обработчик использовал для Taste. Значение по умолчанию true сохраняет поведение строгих экранов.

## Жизненный цикл и пагинация

Category/query reset инвалидирует незавершённый запрос и сбрасывает cursor. Повторные нажатия «Показать ещё» объединяются. Следующая страница сохраняет существующие товары при ошибке, повторяет тот же opaque cursor после обычной сетевой ошибки и подавляет повторяющиеся identity keys. HTTP 422 для устаревшего cursor предлагает загрузить каталог заново. Курсор передаётся буквально; клиент не конструирует его самостоятельно.

Смена аккаунта инвалидирует запросы, очищает catalogue list и блокирует действия старого detail. Ответы прежнего account epoch не применяются. Dispose отменяет debounce и снимает controller listener. Сами API-чтения используют прежние защищённые transport guards.

## Повтор анализа фото

Оба photo upload метода создают случайный 128-bit `Idempotency-Key` перед подготовкой файла. Один логический вызов, включая автоматический 401 refresh/retry, сохраняет ключ. Следующее пользовательское действие получает новый ключ. Публичные сигнатуры upload не изменились.

Для multipart retry после 401 `FormData` клонируется: исходный stream уже finalized, и его прямой повтор ранее не гарантировал отправку фото. Поколение API-сессии также сохраняется до `await MultipartFile.fromFile`; фото прежнего аккаунта не отправляется под новым bearer после окончания чтения файла.

## Доказательства

`test/catalogue_discovery_test.dart` проверяет данные размеров, list/detail, запрет персональных claims/events/complements, stale фильтры/страницы, cursor/retry/dedup, смену аккаунта, capability и поиск → каталог. `test/catalogue_photo_transport_test.dart` проверяет query/detail wire, отмену stale catalogue response и upload replay полных multipart bytes с одним ключом после refresh. Он также проверяет новый ключ для следующего действия и отсутствие dispatch при смене аккаунта во время подготовки файла.

`test/merchant_link_test.dart` сохраняет строгие attribution сценарии и проверяет discovery ledger без рекомендательного event. Существующие detail refresh тесты теперь используют semantic tooltip «Обновить карточку» вместо ошибочной пиктограммы share; проверки актуальности factual reasons сохранены.

Targeted прогон восьми suites: **101 тест прошёл**, `.tmp/catalogue-client-regressions.log`. Static analyze `lib` и четырёх изменённых suites: **без замечаний**, `.tmp/catalogue-analyze.log`. В этих suites присутствуют ранее существовавшие проверки; число не означает 101 новый тест. Итоговый общий functional count и screenshot matrix фиксируются root отдельно.

Просмотрены root contact sheets нового offline capture: 56 состояний, 360/390 px, увеличенный текст, нижний системный inset и открытая клавиатура. Найдена и исправлена одна потеря смысловой подписи: UNKNOWN-unit notice в коротком summary карточки обрезалась ellipsis после размеров/наличия. Теперь она отдельная и неусекаемая. Geometry test на 360 px и text scale 1.6 подтверждает, что целая подпись находится внутри card bounds; все 13 catalogue tests после этого изменения прошли (`.tmp/catalogue-geometry-functional.log`). Root повторно снимет изменённый catalogue layout и выполнит общий прогон. Один blouse JPEG используется только как fixture для разметки; снимки не доказывают качество реальных сочетаний или размерных данных.
