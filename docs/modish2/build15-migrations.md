# Build 15: проверка миграций PostgreSQL

Проверяется переход с `20261013_0025` на `20261015_0028` через настоящий Alembic `env.py`. Это отдельная проверка истории миграций; создание таблиц через `Base.metadata.create_all` её не заменяет.

## Изоляция и запуск

Кластер запускается отдельно. Runner его не запускает и не останавливает. Используется только одноразовый кластер из `.tmp/alpha12-pg-runtime.json`, порт `55439`, база `postgres`, роль `modish_alpha_fixture`. Адрес, порт и роль зафиксированы в коде; входной `DATABASE_URL` игнорируется. Перед созданием и удалением схемы сверяются `SHOW data_directory`, `SHOW port` и `current_database()`.

Все изменения помещаются в новую схему `release15_migrations_<uuid>`. `search_path` содержит только эту схему; доступа через fallback на `public` нет. Схема удаляется в `finally`, включая неуспешные сценарии. Существующие пользовательские схемы не изменяются.

Окружение очищается до загрузки приложения: остаются только необходимые переменные Windows и синтетические настройки теста. Загрузка `.env` отключена. PGOPTIONS строится из проверенной схемы, а не наследуется из окружения. Провайдеры, фиды, рабочий API и SSH не используются.

```powershell
& backend/.venv/Scripts/python.exe -m unittest scripts.test_release15_migration_checks -v
& backend/.venv/Scripts/python.exe scripts/check_release15_migrations.py
```

Успешный runner возвращает одну JSON-строку с `status=passed` и результатами семи сценариев. При ошибке не выводятся URL подключения, значения окружения и SQL-параметры.

## Сценарии

Каждый сценарий начинает с пустой схемы и выполняет все миграции до `0025`. Затем создаёт синтетические старые записи: четыре пользователя, три профиля с сохранённым выбором пола, источник, четыре товара с целыми рублями и границами int32, образ, состояние товара и affiliate-связь.

1. `0025 → 0028 → 0025 → 0028`: цены сохраняют рубли и становятся `NUMERIC(14,2)`; nullable `old_price`, ID, JSON и связи остаются прежними. Существующие выборы пола сохраняются, новый профиль без выбора получает NULL. Новый `recommendation_revision` равен нулю и имеет серверный default. После удаления только контрольного нового профиля downgrade возвращает точный старый снимок данных, типов, default, ограничений и индексов.
2. Копейки в `products.price`: downgrade отклоняется.
3. Копейки в `products.old_price`: downgrade отклоняется.
4. Копейки в `outfits.total_price`: downgrade отклоняется.
5. NULL в `fit_profiles.gender_target`: downgrade отклоняется без назначения пола.
6. Значение выше максимума int32 в `products.price`: downgrade отклоняется.
7. Значение ниже минимума int32 в `outfits.total_price`: downgrade отклоняется.

В шести сценариях отказа заранее записывается `recommendation_revision=7`. После отказа проверяется полный неизменный снимок: версия Alembic остаётся `0028`, колонка revision и её данные сохранены, как и nullable gender, Decimal-цены и ограничения. Это проверяет атомарность полного downgrade через штатную транзакцию Alembic, включая откат уже начатых `0028` и `0027`.

## Результат

20 октября 2026 года: **9 offline guard-тестов успешно**, **7 реальных сценариев PostgreSQL успешно за 9,624 с**. Использован одноразовый локальный кластер на порту `55439`. Лог запуска: `.tmp/build15-migrations-20261020.log`.

Lossless round trip сохранил все старые записи: 4 пользователя, 3 профиля, 1 источник, 4 товара, 1 образ, 1 состояние товара и 1 affiliate-связь. Во всех шести отказах сохранились head Alembic, колонка и значения `recommendation_revision`, остальные данные и ограничения. Все семь созданных UUID-схем удалены.

Это доказательство на синтетических данных локального одноразового PostgreSQL. Копия рабочей базы не использовалась. Проверка не подтверждает миграцию конкретного рабочего backup, не является разрешением на миграцию рабочей базы и не заменяет её резервную копию.
