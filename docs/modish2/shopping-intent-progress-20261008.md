# Shopping Intent: реализация и проверка 8 октября 2026

Это отчёт о текущем этапе нового ТЗ, а не уведомление о выпуске приложения.

## Реализовано

- Подтверждённые размеры по четырём частям гардероба; рост; сохранение исходной системы размера без общих RU/EU/LETTER-конверсий.
- Наличие с временем наблюдения. Чтение, повторная обработка и просмотр не обновляют остатки.
- Общий допуск по полу, размеру, наличию, бюджету и качеству до ранжирования.
- Временные ShoppingIntent: владелец, ключ повтора, версия, срок 24 часа; ограниченный русский parser, явные hard/soft ограничения.
- Выдача до 10 товаров либо до 5 полных образов. Общая цена комплекта, исключения, замена выбранной вещи с фиксацией остальных, повторная проверка при сохранении.
- Повторное чтение проверяет исходные SKU и не ранжирует каталог заново. Устаревшая версия не применяет уточнение дважды.
- Rich Feedback для вещей и частей образа. «Не для задачи» и «слишком дорого» изменяют текущую задачу; персональные причины дают сигнал только указанному признаку.
- Brand affinity учитывает фактические видимые показы. Цены обучаются отдельно по категориям из серверных снимков событий.
- Проверяемые объяснения, события задач, воронка уникальных intent, явное завершение/начало нового запроса.
- Лайк, сохранение, причины отказа, открытие товара и подтверждённый переход к продавцу. Сохранённые товары/образы синхронизируются после действия.

## Ограничения и следующие задачи

1. Каталог не прошёл ворота выпуска: RU-профили не получают точных размерных совпадений; обувь не имеет подтверждённой системы. Корректный поток Style Swipe → завершение онбординга → лента проверен отдельно. Не ослаблять правила ради заполненной выдачи.
2. Для источников с числовыми размерами без системы нужны подтверждённые сведения магазина с точной областью действия. Замер стельки одной модели не доказывает единую EU-систему всех SKU.
3. Parser ограничен поддержанными категориями, цветами, сценариями и отдельными признаками. Неизвестные слова требуют уточнения. Семантическое «похоже на это» пока не реализовано.
4. Образы поддерживают два состава: верх + низ + обувь либо цельная вещь + обувь. Запрос обязательного четвёртого слоя пока не поддержан. При нехватке каталога частичный комплект не выдаётся.
5. В продолжении v17/v18 добавлены все 12 канонических имён событий из ТЗ и отдельные воронки intent/product/outfit. Outfit SizePassRate использует реально проверенные кандидаты, в том числе ранний отказ по обязательному слоту, а не весь каталог. Контракт и основания знаменателей описаны в `shopping-intent-metrics-v17.md`.
6. Benchmark — SQLite и синтетические данные, не PostgreSQL p95 или нагрузка многих пользователей. Проверка интерфейса не подменяет ручной визуальный smoke реального каталога.
7. Рабочий API остаётся build13. Новый APK не выпущен: выпуск зависит от реального каталога и согласованного обновления API/клиента.


## Результат первичного реального аудита v16

Из 53 484 доступных по наблюдению SKU 8 639 имеют распознаваемый размер; у 44 845 он неизвестен либо не подтверждено наличие именно размера. Все 9 351 обувной SKU в этой выборке не имеют достаточного подтверждения системы/наличия размера.

Запросы на брюки и платья для пяти LETTER-профилей дали по 10 позиций: 100 возвращённых товаров прошли повторный допуск. Для RU-профилей обе категории пусты. Ни один из 20 запросов образов не собрал полный комплект. Пустая выдача не считается успешной рекомендацией.

Время одиночных intent-запросов на ограниченном тестовом контейнере: примерно 0,9–2,2 с. Образы: 17–20 с, хотя итог пустой; это отдельная оставшаяся проблема времени ответа. Последовательный smoke с лимитом 0,75 CPU не является production p95 или нагрузочным тестом.

Первичный скрипт пометил онбординг завершённым без Style Swipe. Поэтому его нулевые значения первой ленты не используются как доказательство ошибки ленты: выполнен отдельный smoke с 15 реакциями на реальные товары и вызовом завершения онбординга.

Рабочие контейнеры не менялись. PostgreSQL копии находится на `20261008_0024`; резервная копия тестовой базы: `/opt/modish-releases/20261008-intent-v16/test-before-migration.dump`.


## Дополнительная проверка настоящего онбординга

Все 10 профилей проверены на том же закреплённом образе v16. Пять RU-профилей не получили подходящей стартовой колоды: неизвестную систему нельзя считать RU. Пять LETTER-профилей получили по 20 карточек Style Swipe, прошли по 15 реакций (10 like / 5 dislike), вызов `complete_wow` и первую ленту по 20 карточек.

Фильтр верхней одежды после свайпов: 16 карточек для XS, по 20 для S/M/L/XL. Фильтр обуви: 0 для всех пяти; wow-образы: 0. Время первой ленты в ограниченном контейнере — 11–13 с; время всего smoke одного тёплого профиля — 95–98 с, включая онбординг, три попытки wow, ленту, фильтры и intent. Эти времена требуют отдельной оптимизации до расширения аудитории.

SQL-запрос новой аналитики проверен на PostgreSQL. Тестовые пользователи, реакции, задачи и образы откатились. Образ рабочего API после проверки совпадает с build13.

Синтетические реакции не измеряют удовлетворённость, Like Rate реальных людей либо сходство образов «глазами». Покрытие каталога остаётся неудовлетворительным, выпуск API и APK не выполнен.

Полные машинные отчёты: `intent-v16-stage-report.json`, `intent-v16-catalog-report.json`, `intent-v16-warm-smoke.json`; краткий результат: `intent-v16-validation-summary.json`.


## Продолжение 8–9 октября: v17 и v18

Повтор POST с тем же ключом сохраняет исходный набор результатов: не ранжирует каталог, не увеличивает счётчик generation и в v18 не перезаписывает снимок после перепроверки наличия. Это также устраняет риск затирания контекста более нового уточнения при повторе старой отправки.

Сборка сначала читает только поля типа вещи, затем проверяет обязательную обувь. При отсутствии подходящей обуви описания и исходные JSON остальных вещей не загружаются и одежда не ранжируется. v18 повторно проверяет роль после полного чтения, чтобы исправление категории импортёром не заполнило неверный слот.

Клиент связывает view/like/save/open/merchant click части образа с выбранным outfit. Сервер проверяет принадлежность вещи комплекту. Сохранение и замену повторно нельзя приписать всем образам с тем же SKU. Новые product/outfit-воронки используют реальные view либо явное действие; доставка не считается показом.

v17: точный архив 184 файлов, 282 теста локально и 282 в Docker. Flutter: 60 функциональных тестов, analyze без замечаний. PostgreSQL positive smoke на искусственных SKU показал 4 сформированных / 2 просмотренных комплекта; по одному сохранению, переходу и замене дают 0,5 в соответствующих метриках. Повторный view/save, чужой владелец и неизвестный outfit исключены из корректных знаменателей/числителей. Это проверка аналитического контракта, не покрытие реального каталога.

Повторяемый performance smoke v17 на копии 203 605 товаров: один тестовый профиль LETTER L, RU-профили и настоящий Style Swipe здесь не проверялись. На каждую задачу три запуска, CPU ограничен 0,75, память 768 МБ:
