# Пустой каталог: факты и безопасная диагностика

20 октября 2026, только публичный HTTPS без аккаунта, SSH или изменения данных:

- 17:09:04 UTC: `/health` →200, `database: ok`, `version: 1.0.0-build14`.
- В то же время `/health/ready` →404, `/products/brands?limit=10` →200 `[]`.
- 17:09:05 UTC: `/products?limit=3` →200 `[]`.
- 17:15:33 UTC: одна ранее известная из пользовательского screenshot карточка
  всё ещё доступна напрямую. Наблюдение наличия у неё от 27 мая, состояние
  `unknown`, `is_available: false`.

База поэтому не буквально пуста. Публичная общая выдача и список брендов пусты
без пользовательских фильтров: один только размер L/EU38, рост 166 см, вес 53 кг
или бюджет 100000 не объясняют этот результат. По публичным ответам нельзя
установить свежесть всего текущего ассортимента, активность scheduler или
наличие полных комплектов на размер пользователя. Для этого нужна отдельная
проверка актуальных данных/источников. Настройки, секреты и рабочие данные
при этой разработке не изменялись; старые фиды не импортировались.

## Новый контракт

`GET /catalog/status` возвращает небольшой объект без количества товаров,
источников, raw records или пользовательских сведений:

```json
{
  "status": "refresh_required",
  "scope": "global",
  "personalized": false,
  "checked_at": "2026-10-20T17:20:00+00:00",
  "message": "Магазины ещё не подтвердили актуальное наличие. Каталогу нужно обновление."
}
```

Статус определяется одним SQL SELECT с двумя EXISTS в одной snapshot:

- `ready`: есть хотя бы одно active/is_available/nondeleted/non-demo предложение
  с reported status `in_stock`/`available` и актуальным наблюдением по общим
  правилам 72 часа/допуск будущего времени 5 минут.
- `refresh_required`: такие reported-in-stock предложения есть, но ни у одного
  нет актуального наблюдения. Просроченный, отсутствующий или некорректно будущий
  observation clock требует обновления сведений, а не изменения размера.
- `empty`: нет предложений с указанными базовыми флагами. Это не утверждение,
  что таблица products физически пуста.

`ready` описывает только source availability. Он не подтверждает adult/fashion
admission, цену, размер, пол, source rules, пользовательскую историю или полный
образ. Эти gates по-прежнему применяются перед персональной выдачей.

Endpoint живёт в том же router и имеет ту же alpha-policy, что public products
и brands. При public-mode доступен анонимно; при включённой альфе требуется
разрешённый реальный bearer account. Ответ `Cache-Control: no-store`.
SQL не материализует товары, не считает ассортимент, не обучает вкус и не
обновляет timestamps. Диагностика не является проверкой готовности БД/AI.
Его доступность объявляет общий capability `catalog_status_v1` в
`recommendation_features` status/preferences/WOW. На старом сервере признака
нет, и клиент не должен делать дополнительный запрос ради неподтверждённой
диагностики.

Клиент запрашивает статус после пустой ленты/брендов, если capability присутствует.
На старом сервере 404 или
при сетевой ошибке используется нейтральное сообщение без диагноза. Нельзя
объявлять, что человек просмотрел все вещи или выбрал неверные параметры,
если подтверждения этому нет. Новый endpoint не появляется на рабочем build14
до отдельного выпуска обновления.

В приложении нет встроенного автоматического feed scheduler: есть защищённый
admin sync и CLI `app.scripts.sync_partner_feed`. Упоминание cron в deploy README
описывает backup, а не регулярный импорт. Состояние внешнего scheduler на VPS
по локальному коду установить нельзя. Новый endpoint сам ничего не обновляет.

Дополнительная синтетическая HTTP-проверка задаёт ровно L для верха/низа/платьев,
EU38, рост 166 см, вес 53 кг и бюджет 100000. С независимо размеченными свежими
SKU получаются непустая лента, WOW и полные обычные образы. Это проверка логики,
не доказательство наличия этих размеров в текущем рабочем каталоге.
