# Build15: условия подготовки серверного обновления

20 октября 2026. Это локальная подготовка, не отчёт о deployment.
Сервер, рабочая БД, конфигурация участников и старые Docker images этим
изменением не затрагиваются.

## Что проверено в исходниках

- `backend/Dockerfile` использует backend context и `COPY . .`. Локальный
  `backend/.env` существует; его содержимое не читалось. Ранее `.dockerignore`
  отсутствовал, поэтому обычный build из дерева мог включить приватный файл
  и `.venv` в image. Добавлен `backend/.dockerignore`: исключены env, ключи,
  локальные зависимости, БД, backups, uploads, VCS/cache и build artifacts.
  Runtime `app/`, `alembic/`, `scripts/`, `requirements.txt`, `alembic.ini`
  и исходные CSV/XML test fixtures сохранены; безопасный `.env.example` разрешён.
- `deploy/docker-compose.prod.yml` — шаблон с service `api`/`db` и ролью
  `modish`, без Redis. Сохранённый build14 deployment использовал project
  `modish`, service `backend`, alias `postgres`, роль `modish_user` и Redis.
  Шаблон нельзя принимать за проверенную конфигурацию работающего VPS.
- Default `backend/scripts/entrypoint.sh` сначала запускает
  `alembic upgrade head`, затем API. Запуск candidate со штатным CMD и рабочим
  DATABASE_URL уже является изменением схемы, а не предварительным smoke.
- Старый `release14_activation_remote.py` содержит версии/images/revisions
  build14/0025 и не является готовым runner для build15/0028.

Правила Docker context проверены по фактическому `COPY` и текущим runtime
файлам: код Python, shell entrypoint, Alembic `.mako` и зависимости не
исключаются. Отдельный парсер Dockerignore или зеркальные unit-тесты не
добавлялись. Docker CLI не найден в PATH при этой проверке; настоящий context
не собирался и image layers не осматривались. Новые исключения не удаляют
приватные данные из ранее созданных images/cache. Сборка из проверенного
staging context остаётся предпочтительной.

## До изменения production

Новый preflight должен получить фактические Compose labels/config files,
image ID, сети, DB identity и volume текущих контейнеров. Сравнение должно
быть с сохранённым согласованным baseline; имена из шаблона не заменяют
эту проверку. Выбранный immutable package проверяется по commit, внешнему
SHA-256 и manifest; его staging не смешивается с локальными `.env` или `.venv`.

Нужен свежий согласованный backup с проверенным восстановлением в отдельную
копию PostgreSQL. На этой копии выполняются переход `0025 → 0028`, smoke
на реальных сохранённых SKU и проверка выбранного API rollback-пути.
Изолированные синтетические [migration checks](build15-migrations.md) уже
прошли, но не проверяли конкретный рабочий backup и свежесть ассортимента.
Неизвестная обувная система не становится подтверждённой после миграции.

## Миграция и переключение API — отдельные операции

Перед рабочим upgrade нужен согласованный maintenance-порядок: остановить
пишущие API/фоновые импорты, зафиксировать финальный backup и текущий head,
выполнить миграцию отдельным одноразовым процессом и проверить результат.
После этого API запускается с явно заданным запуском без повторного
автоматического upgrade; проверяются строгая `/health/ready`, версия build15
и согласованный smoke перед возобновлением записей.

Нельзя обещать автоматический downgrade или восстановление старого backup
после появления новых записей. Миграции намеренно отказывают в downgrade
при копейках, значениях вне int32 и NULL gender. API rollback на схеме0028
нужно доказать отдельно; старый entrypoint не знает нового Alembic head.
Если совместимый rollback не доказан, требуется отдельный maintenance/restore
план с явными последствиями для новых данных.

Для закрытой альфы белый список включается только с согласованным набором
адресов; исходный default-off не ограничивает доступ сам по себе. Выбор
публичного релиза, выдача APK, изменение конфигурации и deployment остаются
отдельными решениями. Наличие package/migration helpers не означает, что
эти production-действия уже выполнены.
