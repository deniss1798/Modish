# 1.3 — квота фото и повтор после потерянного ответа

Локальные изменения 16 октября 2026. Production и настоящий AI-провайдер не
использовались. Существующий backend reservation protocol сохранён:
короткое резервирование/списание, внешний вызов без открытой транзакции,
короткое завершение либо возврат квоты после подтверждённой остановки.

## Исправление клиента

До изменения ключ переживал автоматический 401 refresh, но ручной повтор
после обрыва связи создавал новый ключ и мог повторно списать квоту.
Теперь ApiClient хранит одну незавершённую попытку для каждой из двух операций:
онбординг и анализ из профиля. Ключ, неизменяемые байты, MIME, имя файла и
multipart boundary используются повторно для того же фото.

Сетевая ошибка, pending 409, неподтверждённая операция и неизвестный ответ
прокси, в том числе HTML/JSON array с HTTP200, сохраняют попытку. Подтверждённое
завершение или известная ошибка
остановленного/возвращённого backend задания освобождают только соответствующую
попытку. Поздний ответ предыдущего фото не очищает новую попытку.

Новый файл/содержимое/операция получает отдельный ключ. Смена аккаунта и dispose
очищают попытки; epoch проверяется до и после подготовки файла и в транспорте.
Фото ограничено 5 MiB до чтения в память и при чтении потока.
Внешние зависимости и публичные сигнатуры API-клиента не изменены.

Содержимое и ключ живут только в памяти текущей сессии приложения. Это не
восстановление незавершённого запроса после закрытия процесса; фотографии
дополнительно не сохраняются на диск.

## Доказательства

Новые PostgreSQL проверки используют реальный HTTP и фиктивный провайдер.
Все три теста выполняются для обоих endpoints:

- два одновременных ключа при последнем слоте: один вызов провайдера, один
  успешный анализ, один отказ по квоте и ровно одно списание;
- одинаковый ключ: один вызов, pending 409, затем точный replay без нового
  списания, ревизии или анализа;
- во время внешнего вызова все job Sessions закрыты, pool свободен; feedback
  и изменение профиля того же пользователя завершаются до освобождения
  провайдера, их данные переживают completion.

Новые PostgreSQL: **3/3**, 1,380 с; isolated workspace cluster остановлен,
PID-файл отсутствует. Существующие SQLite lifecycle проверки покрывают
refund/cancellation/expiry/supersession/month transition и response replay.

Финальная приёмка текущего дерева:

- Backend **840**, 107,112 с, успешно; 50 opt-in PG пропущены в SQLite run.
  Ранее принятые 47 PG + новые **3/3** проверены отдельными запусками.
