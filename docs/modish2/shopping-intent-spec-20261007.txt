# Техническое задание на доработку текущей версии Modish

## 1. Цель доработки

Текущая версия Modish представляет собой персонализированную fashion-рекомендательную систему с лентой товаров, User Twin, MIE-ranking, Outfit Engine и сбором пользовательской обратной связи.

Основная задача следующего этапа — перейти от модели:

**«показывать пользователю товары, которые ему, вероятно, понравятся»**

к модели:

**«понимать текущую задачу пользователя и предлагать конкретные доступные товары и образы, которые подходят ему по стилю, размеру, бюджету и контексту покупки».**

Система должна начать учитывать не только taste-профиль пользователя, но и:

- точный размер;
- фактическую доступность размера;
- бюджет;
- текущий shopping intent;
- occasion;
- ограничения;
- характеристики посадки;
- историю поведения;
- предпочтения по брендам;
- контекст конкретной сессии.

---

# 2. Текущее состояние системы

На момент постановки задачи в Modish уже имеются:

- Flutter-клиент;
- FastAPI backend;
- PostgreSQL;
- каталог товаров;
- импорт товарных фидов;
- нормализация части товарных данных;
- User Twin;
- Taste/Fit/Style-профили;
- MIE ranking;
- candidate retrieval;
- hard filters;
- персональная лента;
- Outfit Engine v2;
- события:
  - impression/view;
  - skip;
  - dislike;
  - like;
  - save;
  - open product;
  - affiliate/buy click;
- behavioral learning;
- базовые embeddings;
- diversity/exploration;
- аналитика и benchmark рекомендательной системы.

Текущий MIE концептуально оценивает:

- Taste;
- Fit;
- Context;
- Quality;
- Exploration.

Основной проблемой текущего состояния является недостаточность данных для действительно персональной fashion-рекомендации.

Критические ограничения:

1. размер пользователя не является гарантированным обязательным параметром;
2. в части сценариев используется fallback/default размер;
3. наличие нужного размера недостаточно строго участвует в eligibility;
4. recommendation engine в первую очередь определяет вероятность симпатии к товару, а не соответствие текущей shopping-задаче;
5. контекст покупки пользователя практически не выражен;
6. Outfit Engine недостаточно связан с конкретным пользовательским intent;
7. данные различных магазинов требуют более строгой нормализации;
8. брендовые предпочтения практически не используются как самостоятельный сигнал;
9. пользователь не может нормально сформулировать сложную задачу естественным языком.

---

# 3. Ключевой принцип новой версии

Pipeline должен быть разделён на пять логических стадий:

**User Intent → Eligibility → Candidate Retrieval → Personal Ranking → Composition**

То есть:

1. понять, что пользователь сейчас хочет;
2. исключить физически неподходящие товары;
3. получить релевантный candidate pool;
4. персонально ранжировать его;
5. при необходимости собрать из товаров законченный outfit.

MIE не должен пытаться компенсировать плохие исходные данные.

Если товара нет в нужном размере, он не должен получать низкий score.

Он вообще не должен попадать в ranking.

---

# 4. P0 — обязательные изменения

## 4.1. Размер пользователя

### Требование

Размер одежды должен стать полноценной обязательной частью Fit Profile.

Fallback вида:

`size = M`

не должен использоваться как реальный размер пользователя.

Если размер неизвестен, система должна явно работать в состоянии:

`size_unknown`.

### User Twin должен хранить как минимум

- верх;
- низ;
- платье/общий размер;
- обувь;
- рост.

Структура должна предусматривать дальнейшее расширение на:

- грудь;
- талию;
- бёдра;
- длину ноги;
- посадочные особенности.

На данном этапе эти дополнительные измерения не являются обязательными.

### Acceptance criteria

Пользователь с размером 48 не получает товар, доступный только в размере 44.

Если размер товара невозможно определить, система должна иметь отдельную policy для `unknown_size`, а не считать такой товар подходящим автоматически.

---

# 4.2. Нормализация размеров

Создать отдельный слой:

**Size Normalization / Size Resolver.**

Он должен приводить магазинные значения:

`S`  
`M`  
`L`  
`42`  
`44`  
`46`  
`W28`  
`EU 38`

к нормализованному представлению.

Оригинальное значение магазина при этом должно сохраняться.

Рекомендуемая структура:

`raw_size`

`normalized_size`

`size_system`

`category`

`merchant_id`

`availability`

В дальнейшем архитектура должна позволять подключить отдельные size mappings для конкретных брендов.

---

# 4.3. Exact-size eligibility

Проверка размера должна выполняться **до MIE ranking**.

Pipeline:

`candidate`

→ gender eligibility

→ category eligibility

→ size eligibility

→ availability eligibility

→ price/budget eligibility

→ MIE.

Не допускается:

`нет размера → MIE score уменьшен`

Требуется:

`нет размера → candidate исключён`.

---

# 4.4. Availability

Ввести явное состояние доступности товара.

Минимальные состояния:

- available;
- unavailable;
- unknown;
- stale.

Неактуальные товары не должны доминировать в выдаче.

Для товара необходимо хранить как минимум:

- timestamp последнего обновления;
- active status;
- доступные размеры;
- текущую цену.

Рекомендуется предусмотреть `availability_confidence`.

---

# 4.5. Shopping Intent

В систему необходимо добавить новую сущность:

**ShoppingIntent.**

Она описывает не пользователя вообще, а его **текущую задачу**.

Пример:

> Мне нужны брюки в офис до 7000 рублей.

Должно превращаться примерно в:

`category = trousers`

`occasion = office`

`budget_max = 7000`

`intent_type = single_item`

Другой пример:

> Собери мне образ на свадьбу до 20 тысяч, только без платья и каблуков.

Внутреннее представление:

`intent_type = outfit`

`occasion = wedding`

`budget_max = 20000`

`exclude_categories = dress`

`exclude_features = heels`

### Минимальные поля ShoppingIntent

- intent_type;
- requested_categories;
- excluded_categories;
- occasion;
- budget_min;
- budget_max;
- colors/preferences;
- exclusions;
- free_text;
- created_at;
- expires_at или active flag.

Shopping Intent не должен навсегда записываться в Taste Profile пользователя.

Например:

> «Мне нужна красная блузка на корпоратив»

не означает:

> «пользователь вообще любит красную одежду».

---

# 4.6. Natural Language Shopping Request

На главном экране должен появиться способ сформулировать задачу обычным текстом.

Примеры:

> Что надеть на свадьбу?

> Нужны нормальные джинсы до 6000.

> Собери образ в офис.

> Хочу что-то похожее на это пальто, но дешевле.

> Мне нужны брюки, но не широкие.

На первом этапе допускается ограниченный parser, если полноценный semantic parser ещё не внедряется.

Критически важно разделять:

**hard constraints**

и

**soft preferences**.

Например:

> «до 10 000»

hard constraint.

> «желательно чёрное»

soft preference.

> «только не платье»

hard exclusion.

---

# 4.7. Session Context

Добавить временный контекст сессии.

Он должен позволять пользователю уточнять запрос:

> дешевле;

> более повседневное;

> другого цвета;

> только не оверсайз;

> покажи более классическое;

> замени брюки;

> оставь верх, поменяй обувь.

Эти уточнения не должны автоматически переписывать долгосрочный User Twin.

Нужно разделить:

**User Twin**

и

**Session Context**.

User Twin = долгосрочные предпочтения.

Session Context = чего человек хочет сейчас.

---

# 4.8. Outfit Engine

Outfit Engine должен перейти от общего rules-based формирования комплектов к задаче:

**собрать лучший outfit под ShoppingIntent + User Twin.**

Вход:

- User Twin;
- Shopping Intent;
- eligible products;
- ограничения;
- budget;
- occasion.

Выход:

- полный outfit;
- total price;
- constituent products;
- confidence;
- explanation;
- возможные альтернативы.

### Hard constraints outfit

Каждый товар:

- подходит по полу;
- подходит по размеру;
- доступен;
- не нарушает exclusions.

Весь комплект:

- соответствует occasion;
- укладывается в бюджет, если задан жёсткий budget_max;
- содержит необходимые outfit slots.

---

# 5. P1 — развитие персонализации

## 5.1. Brand Affinity

Не добавлять пока обязательный вопрос:

> «Ваши любимые бренды».

Причина:

каталог Modish пока не содержит достаточно брендов, чтобы гарантировать пользователю наличие выбранных вариантов.

При этом backend уже должен автоматически формировать brand affinity.

Добавить в User Twin:

`brand_affinity`

`brand_negative_affinity`

`brand_exposure_count`

Brand affinity рассчитывать по поведению:

- impressions;
- likes;
- saves;
- dislikes;
- skips;
- product opens;
- affiliate clicks.

Обязательно учитывать exposure.

Пример:

3 лайка бренду после 4 показов — сильный сигнал.

3 лайка после 100 показов — слабый сигнал.

### Ограничение

Brand affinity не должен быть hard filter.

Любимый бренд является сигналом ranking, а не требованием.

---

# 5.2. Product DNA

Персонализация должна постепенно переходить от простых category/color preferences к характеристикам самого изделия.

Для товара желательно хранить:

- category;
- subcategory;
- color;
- color family;
- silhouette;
- fit;
- length;
- rise;
- sleeve;
- neckline;
- pattern;
- material;
- style;
- occasion;
- season;
- formality;
- price band;
- brand.

Цель:

система должна понимать не только:

> пользователю нравится бренд X,

но и:

> пользователю часто нравятся вещи бренда X с прямым силуэтом, нейтральными цветами и минималистичным стилем.

Это позволит рекомендовать похожие товары других брендов.

---

# 5.3. Price Profile

Бюджет пользователя не должен быть одним глобальным числом.

В перспективе необходимо формировать category-specific price profile.

Например:

`tops = 3000–6000`

`jeans = 5000–9000`

`outerwear = 12000–25000`

`shoes = 7000–15000`

Профиль должен обучаться на:

- likes;
- saves;
- clicks;
- purchases/affiliate clicks;
- skips/dislikes с учётом цены.

---

# 5.4. Rich Feedback

Существующий like/dislike/skip сохранить.

Для части негативных действий добавить необязательное уточнение причины:

- не нравится стиль;
- дорого;
- не мой цвет;
- не моя посадка;
- не нравится бренд;
- уже есть похожее;
- не подходит для задачи.

Причина должна записываться отдельно от общего dislike.

Пользователя нельзя заставлять выбирать причину после каждого свайпа.

---

# 5.5. Explainability

Для персональных рекомендаций добавить короткое объяснение.

Примеры:

> Подходит под ваш бюджет и размеры.

> Вы часто сохраняете прямые брюки нейтральных цветов.

> Подходит для офиса и сочетается с выбранным жакетом.

> Этот бренд вам часто нравится.

Запрещено генерировать объяснение, которое не подтверждается фактическими данными User Twin/Product DNA.

---

# 6. MIE — изменение scoring

Текущую концепцию:

Taste + Fit + Context + Quality + Exploration

сохранить.

Но поменять ответственность компонентов.

## Eligibility

Вообще не является score.

Это hard filtering:

- gender;
- size;
- stock;
- category restrictions;
- hard budget;
- explicit exclusions.

## Ranking

В ranking участвуют:

### Taste

Насколько товар соответствует долгосрочным предпочтениям.

### Fit

Насколько характеристики товара соответствуют fit-profile пользователя.

Fit не заменяет проверку наличия размера.

### Context

Насколько товар соответствует текущему Shopping Intent:

- occasion;
- requested category;
- season;
- formality;
- current task.

### Quality

Качество и достоверность товарной карточки.

### Exploration

Контролируемое исследование новых вариантов.

### Brand affinity

Не рекомендуется выделять бренд в отдельный крупный score.

Лучше включить его как feature внутри Taste.

---

# 7. Архитектура User Twin

User Twin должен быть логически разделён на блоки.

## Identity / static

- gender;
- age group;
- height.

## Fit Profile

- clothing sizes;
- shoe size;
- будущие body measurements;
- fit preferences.

## Taste Profile

- style vector;
- color vector;
- category vector;
- Product DNA preferences;
- brand affinity.

## Price Profile

- global budget;
- category price bands;
- price sensitivity.

## Behavioral Profile

- interaction history;
- negative signals;
- saves;
- clicks;
- purchases;
- exposure counts.

## Confidence

Каждая learned preference должна иметь confidence.

Система должна различать:

> «пользователь не любит красный»

и

> «нам пока недостаточно данных, любит ли пользователь красный».

---

# 8. Изменения интерфейса

## Onboarding

Обязательно:

1. пол;
2. размер одежды;
3. рост;
4. размер обуви;
5. базовый бюджет/ценовой диапазон;
6. Style Swipe.

Не делать обязательным:

- любимые бренды;
- фото;
- body measurements;
- длинную стилистическую анкету.

---

## Home

На Home должны существовать два способа взаимодействия.

### Discovery mode

Текущая персональная лента.

Используется для:

- изучения вкуса;
- discovery;
- casual browsing.

### Intent mode

Поле:

**«Что вы ищете?»**

или аналогичный интерфейс.

Пример:

> Собери мне образ на свидание.

После отправки запрос создаёт Session Context и ShoppingIntent.

---

## Recommendation results

При intent-запросе выдача должна в первую очередь показывать не бесконечный feed, а ограниченное количество лучших решений.

Например:

**3–10 товаров**

или

**3–5 outfits**.

Для каждого результата:

- цена;
- магазин;
- доступный размер;
- причина рекомендации;
- действия like/save/dislike;
- переход к продавцу.

# 11. Что НЕ делать на этом этапе

Следующие функции в scope текущей доработки не входят:

- virtual try-on;
- генерация одежды;
- сложный computer vision тела;
- полноценный digital wardrobe;
- 3D fitting;
- автоматическое определение размеров по фотографии;
- explicit favourite brands onboarding;
- checkout внутри Modish;
- собственная логистика;
- advanced collaborative filtering;
- сложная ML-модель размера;
- полноценный learned outfit transformer;
- глобальная замена MIE нейросетью.

Эти задачи не должны блокировать текущую Alpha.

# 12. Порядок реализации

## Этап 1. Catalog/Fit foundation

1. нормализация размеров;
2. availability;
3. exact-size eligibility;
4. обязательный size-profile;
5. исправление fallback/default size;
6. quality checks каталога.

### Definition of Done

В персональную выдачу не попадает товар, который заведомо невозможно купить пользователю в его размере.

---

## Этап 2. Shopping Intent

1. модель ShoppingIntent;
2. Session Context;
3. parser запроса;
4. natural-language input;
5. hard/soft constraints;
6. intent-aware retrieval;
7. Context scoring.

### Definition of Done

Пользователь может написать:

> Нужны чёрные брюки в офис до 7000.

и получить только релевантные доступные варианты в своём размере.

---

## Этап 3. Intent-aware Outfit Engine

1. occasion;
2. budget;
3. outfit slots;
4. exclusions;
5. personal ranking;
6. replace item.

### Definition of Done

Пользователь может написать:

> Собери образ на свадьбу до 20 000 без платья.

и получить законченные комплекты из доступных товаров.

---

## Этап 4. User Twin 2.0

1. brand affinity;
2. Product DNA;
3. price profile;
4. richer negative feedback;
5. confidence model.

### Definition of Done

Система постепенно понимает не только конкретные понравившиеся SKU, но повторяющиеся характеристики товаров.

---

## Этап 5. Explainability

Добавить фактическое объяснение рекомендаций.

### Definition of Done

Каждое объяснение основано на реально существующих данных пользователя, товара или текущего intent.

---

# 13. Критические acceptance scenarios

## Scenario 1

Пользователь:

размер 48.

Товар:

доступен 42, 44, 46.

### Expected

Товар не попадает в candidate ranking.

---

## Scenario 2

Пользователь:

> Хочу платье до 8000.

Товар:

цена 12 000.

### Expected

Если budget является hard constraint — товар исключён.

---

## Scenario 3

Пользователь:

> Нужен образ без каблуков.

### Expected

Outfit Engine не имеет права включить обувь на каблуке.

---

## Scenario 4

Пользователь обычно любит casual, но запросил:

> образ на свадьбу.

### Expected

Context должен временно повысить формальность рекомендаций.

Taste Profile пользователя при этом не меняется на formal.

---

## Scenario 5

Пользователь часто лайкает определённый бренд.

### Expected

Brand affinity постепенно увеличивается.

Другие бренды не исключаются.

---

## Scenario 6

Любимого бренда нет в каталоге.

### Expected

Система продолжает использовать Product DNA и предлагает стилистически близкие товары.

---

## Scenario 7

Пользователь пишет:

> слишком дорого.

### Expected

Изменяется Session Context / price constraint текущей задачи.

Глобальный Taste Profile не должен воспринимать это как dislike стиля показанных товаров.

---

# 14. Целевое состояние после реализации

После выполнения данного ТЗ Modish должен перестать быть только персонализированной fashion-лентой.

Пользователь должен иметь возможность:

**1. просто листать персональную ленту;**

или

**2. поставить системе конкретную shopping-задачу.**

Например:

> Мне нужны джинсы.

> Найди куртку до 15 тысяч.

> Собери образ в офис.

> Что надеть на свадьбу?

> Хочу что-нибудь более классическое.

> Покажи дешевле.

> Замени обувь в этом образе.

При этом Modish должен использовать одновременно:

**User Twin + Shopping Intent + Fit + товары магазинов + availability + персональный ranking + Outfit Engine.**

Главная продуктовая формула следующей версии:

**Understand → Filter → Rank → Compose → Learn.**

То есть:

**понять задачу → исключить неподходящее → персонально выбрать лучшее → собрать решение → обучиться на реакции пользователя.**

Именно эта архитектура должна стать основой следующего этапа Modish.
