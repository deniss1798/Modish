# Modish: build14, состояние на 14 октября 2026

Код и APK build14 подготовлены. Рабочий API пока остаётся на закреплённом образе
build13, с миграцией `20260917_0021`; импорт в production не выполнялся.
Проверенный план переключения готов, но перенос четырёх фидов в рабочую базу
ожидает отдельного согласия: прежнее разрешение было только на изолированную копию.

## Изменения

- Отдельный каталог одежды и обуви с поиском, фильтрами и пагинацией. Он доступен
  до завершения обучения вкуса и из пустой персональной ленты, сохраняет выбранную
  категорию/запрос. Фото, цена, наличие, возрастная категория, пол, бюджет и прочие
  ограничения проверяются; соответствие размера пользователю не обещается.
- Каталог постоянно показывает «Размер нужно уточнить у магазина» и отдельно
  сообщает о неизвестной системе размеров. Карточка открывает магазин; каталог
  не добавляет лайки/сохранения и не обучает TasteProfile. Строгие лента/WOW/Intent
  сохраняют проверку размера. [Контракт](catalogue-discovery-contract-20261014.md),
  [клиент](catalogue-client-handoff-20261014.md).
- Анализ фото получил короткую транзакцию резервирования квоты и устойчивый ключ
  повторного запроса. Соединение с БД освобождается до ожидания провайдера;
  повторный запрос получает результат уже завершённой операции. Ошибка/отмена
  возвращает квоту один раз в исходном периоде. Поздний ответ не переписывает более
  новую операцию. Клиент сохраняет ключ при повторе после 401 и допускает время
  ожидания провайдера. [Ограничения и восстановление](photo-reservations-20261014.md).
- Конкурентная регистрация одного email даёт один аккаунт и корректный 409;
  ошибки иных ограничений БД не маскируются как дубликат email.
- Исправлена нехватка карточек при разнообразии категорий: алгоритм сохраняет
  необходимые разделители для полной колоды, если каталог позволяет её собрать.
  Ограничение повторов категории остаётся. Порядок колоды может измениться;
  эквивалентность хешей со старой ревизией не утверждается.
- Проверка сохранения ID при импорте использует только три лёгких поля товара,
  без загрузки всех сырых фидов и размерных свидетельств в ORM. Это устранило OOM
  первой попытки на копии; лимит контейнера остался 1536 МБ.

## Выпуск и откат

APK: `Modish-1.0.0-build14.apk`, versionCode 14; подпись совпадает с build13.
Файл в папке Downloads пользователя; APK не включён в Git. Данные, окружение и
дампы также не включены. Образ кандидата и исходный архив закреплены хешами в плане.

План проверяет оба действующих Compose-файла в исходном порядке и сравнивает
полную объединённую конфигурацию. При активации меняется только исполнение backend;
PostgreSQL/Redis сохраняют контейнеры. Перед миграцией создаётся согласованный
pg_dump с проверкой TOC и включается старый API с блокировкой двух фото-маршрутов.
Затем следуют аддитивные миграции 0021→0025, однократный одобренный импорт и новый API.

Откат возвращает защищённый старый API, сохраняя схему, каталог и ledger фото.
Обычный старый API нельзя включать поверх нового ledger: он обойдёт резервирование.
Автоматического восстановления дампа, downgrade или повтора неоднозначного COMMIT нет.
Снимки от 12 октября сохраняют реальные времена наблюдения и принимаются только
до предела 72 часа. Обработка не продлевает наличие товара.

## Что ещё не готово

- Системы размеров обуви в текущих фидах не подтверждены; наличие полного каталога
  для просмотра не доказывает покрытие строгих полных образов.
- Длительная блокировка владельца во время ранжирования feed/Intent остаётся P1.
  Нужны версионированный снимок входов, ранжирование вне write-lock и короткая
  повторная проверка перед выделением карточек; нельзя просто удалить блокировку.
- Не измерены production p95/нагрузка, планы запросов и необходимость новых индексов.
- Клиентский ключ фото сохраняется в рамках одной операции и повтора 401;
  отдельный ручной повтор после потерянного ответа ещё не возобновляет старый ключ.
- Нужен последующий процесс регулярного получения актуальных фидов; этот план
  разрешает только четыре конкретных проверенных снимка, а не бессрочный импорт.

Поэтому build14 не обозначает выполнение всего ТЗ или готовность приложения
во всех сценариях. Действующий сервер и последующие архитектурные задачи
учитываются отдельно.
