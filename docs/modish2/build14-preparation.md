# Подготовка build14 на изолированной копии

Актуальный результат: подготовка закончилась успешно, включая HTTP smoke и
каталог на десяти профилях. [Полный отчёт](build14-bounded-report.json),
[проверенный план активации/отката](build14-activation-plan.json),
[состояние релиза](engineering-progress-20261014.md). Production не изменён.
Ниже описан исходный сценарий подготовки; первая попытка сохранена как диагностика.
Продолжение исправило путь монтируемых тестов, затем OOM проверки ID: новый
`release14_import_bounded.py` читает тонкую проекцию ID/source/external_id.
`release14_validate_bounded_remote.py` проверил откат незавершённой транзакции
перед единственной повторной попыткой, без повторного восстановления базы.

`scripts/release14_prepare_remote.py` — проверяемый сценарий подготовки, а не
активации релиза. Само наличие этого файла не означает, что проверки PostgreSQL
или подготовка на VPS уже выполнены. Он запускается ответственным за релиз только
после проверки кода и разрешения на соответствующие действия.

Фиксированная папка: `/opt/modish-releases/20261014-build14`. В неё заранее
загружаются `source.tar`, `release14_prepare_remote.py`, `check_photo_postgres.py`,
`release14_import_clone.py`, исходный `intent_v20_refresh_import.py` и, для полного
отчёта подготовки, `check_discovery_postgres.py`. SHA-256 каждого изменяемого
помощника и архива передаётся явно. Число unit-тестов берётся из успешной проверки
именно этого архива. Пример формы команды без конкретных хешей:

```sh
python3 release14_prepare_remote.py \
  --archive-sha256 "$ARCHIVE_SHA256" \
  --expected-tests "$VERIFIED_TEST_COUNT" \
  --photo-helper-sha256 "$PHOTO_HELPER_SHA256" \
  --import-helper-sha256 "$IMPORT_HELPER_SHA256" \
  --discovery-helper-sha256 "$DISCOVERY_HELPER_SHA256"
```

Сценарий проверяет неизменный production-образ build13, текущую миграцию 0021,
хеши файлов архива и безопасные пути распаковки. Он собирает слой исходников на
закреплённом базовом образе без сети и установки пакетов, затем сверяет файлы в
образе и запускает unit-тесты с сетью `none`.

Production PostgreSQL используется только для проверки ревизии и согласованного
`pg_dump` с `default_transaction_read_only=on`. Дамп остаётся на VPS в закрытой
папке `privatebackup`; окружение и подробные журналы — в `private`. Сценарий не
выводит их содержимое. Секреты production не переносятся в окружение приложения
для проверок: оно содержит только URL существующей тестовой PostgreSQL с новым
именем базы, случайный JWT-секрет и явные тестовые настройки без ключей AI.

В существующем контейнере `modish_foundation_test_pg` создаётся новая база
`modish_build14_test`. Если такая база уже существует, сценарий прекращает работу.
База `modish_test` не перезаписывается. После восстановления новая база мигрирует
до `20261013_0025`. Реальные конкурентные проверки обоих фото-маршрутов используют
контролируемый провайдер без внешних вызовов; также проверяется конкурентная
регистрация одинакового адреса. Удаляются только созданные этим тестом записи.

Четыре существующих снимка Baon, Shopping Live, Serginnetti и Post Meridiem
копируются из `20261009-intent-v20/refresh-20261013/feeds` без загрузки новых фидов.
Сохраняются байты, хеши и исходные времена наблюдений. Предельный возраст — 72 часа;
просроченные снимки требуют отдельного нового получения данных, а не изменения
дат. Импортер отличается от закреплённого исходника ровно семью проверяемыми
заменами, включая имя новой базы и ревизию 0025. Сохраняются ограничения размера и
числа строк, атомарная транзакция и строгая проверка старых идентификаторов товаров.
Состояние источников вне этих четырёх сравнивается до и после импорта.

Необязательный помощник discovery проверяет каталог на десяти профилях через
сервисные функции и откатывает каждую транзакцию с тестовым профилем. Это отдельное
свидетельство от HTTP smoke и не подтверждает готовность полных образов или точное
соответствие размеров. Без этого помощника отчёт остаётся
`code_and_clone_import_checked_catalogue_acceptance_pending`. При его успехе —
`prepared_ready_for_review`. В обоих случаях `ready_for_activation=false`:
HTTP smoke, разрешение на импорт production и проверка активации/отката остаются
отдельными пунктами.

При ошибке сохраняются новая база, резервная копия и диагностические файлы;
автоматического удаления или повторного восстановления поверх существующей базы
нет. Завершается только точный временный контейнер, созданный данным запуском.
Повторный запуск в той же папке намеренно запрещён. Исправления и повторная попытка
требуют проверенного нового сценария с новым каталогом и именем базы.

Правила восстановления фото-квоты и ограничения отката приложения описаны в
[photo-reservations-20261014.md](photo-reservations-20261014.md).
