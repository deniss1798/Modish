# Каталог: размерная проверка и отдельный режим просмотра

12 октября 2026. Исследование публичных первичных источников; приложение, сервер и фиды не изменялись. Новых сообщений магазинам, входов и покупок не было. Подробные факты сохранены в [JSON](catalog-unlock-research-20261012.json).

## Что удалось подтвердить

[Официальная спецификация Admitad для рекламодателей](https://support.admitad.ru/article/ru/206.html) разрешает объединять варианты одного товара по размерам/цветам для сценариев без ReTag. `available` относится к товару; документ не задаёт общую RU/EU-систему размера. Поэтому общий формат не заменяет контракт конкретного экспортного поля, а наличие модели не доказывает наличие каждого её варианта.

В [Shopping Live / CAPRICE 195449](https://www.shoppinglive.ru/p/krossovki-iz-oleney-kozhi-na-podkladke-iz-iskusstvennogo-meh-195449) размер 39 выбран в чёрном цвете. После загрузки UI показывает «Нет в наличии». Кнопки размеров 36–42 видны, но имеют CSS-признак отключённого состояния; HTML `disabled` отсутствует. Нельзя использовать существование кнопки или `isEnabled()` как подтверждение наличия. Публичной JSON-LD-разметки в документе не было. Характеристики дают длину стельки в сантиметрах; размерная панель рекомендует запас 0,5–1 см к длине стопы. RU/EU и привязка кнопки к offer ID не доказаны.

В [Shopping Live / ARA 215501](https://www.shoppinglive.ru/p/vysokie-krossovki-s-innovatsionnoy-tehnologiey-high-soft-215501) также указаны модельные длины стельки, но национальная система числовых вариантов не подписана.

**Вывод:** новых оснований для массовой конверсии или ограниченного включения конкретных моделей в exact-size подборку нет. Справочник сантиметров можно показывать как модельные мерки, но он не превращает число магазина в EU/RU и не подтверждает посадку по имеющемуся пользовательскому EU-размеру.

## Политика, которая позволит пользоваться неполным каталогом честно

Это архитектурное предложение для review. Оно не включено и не засчитывается как выполнение exact-fit/full-outfit критериев ТЗ.

Разделить допуск по цели использования, а не ослаблять общий `exact_size_match`:

| Цель | Допуск unknown size | Обещание размера | Сохранение/метрики |
| --- | --- | --- | --- |
| Первая персональная лента, intent-результат, WOW | Нет | Только подтверждённая система и актуальное наличие размера | Текущие строгие правила |
| Каталог по явному запросу пользователя | Да, отдельно обозначенный режим | Исходная маркировка магазина, без утверждения о соответствии профилю | Сохранение товара допустимо; событие и выдача имеют `discovery` scope |
| Полный образ в персональной подборке | Нет для каждого обязательного слота | Все слоты проходят строгую проверку | Отдельный просмотр не считается валидным образом |

UX: при нулевом строгом результате сохранить объяснение причины и предложить действие «Посмотреть каталог без проверки размера». Пользователь сам открывает каталог. Заголовок «Каталог», фильтр «Размер не проверен». На карточке: «Размер магазина: 39 · система не указана». Действие «Проверить размер у магазина» ведёт на проверенную публичную карточку. Утверждения «Есть ваш размер», «Подходит вам», конкретное соответствие EU/RU отсутствуют. Не переименовывать этот экран в персональную ленту и не пускать холодного пользователя мимо Style Swipe в неё.

Остальные hard gates сохраняются: взрослый fashion-товар, запрошенный пол/категория, бюджет, действительная цена/валюта, фото, рабочая партнёрская ссылка, свежее наблюдение наличия товара и исключение уже просмотренных дублей. Известный отрицательный stock остаётся отрицательным; discovery разрешает только неизвестный fit, а не неизвестное/просроченное наличие. Если пол неизвестен, не выдавать товар как совпадающий с пользовательским полом. Не использовать discovery как скрытый fallback ответа строгого endpoint.

API должен явно вернуть `selection_policy`, `fit_status`, неизменённый `merchant_size_label`, `fit_evidence` и `availability_scope`. Рекомендательная логика не должна считать `fit_status=unknown` положительным Fit. Общие gates и identity повторно использовать из одного модуля; size gate подключать через явную политику. Не добавлять разбросанные `strict=False` в существующие сервисы. Вход в discovery — отдельный endpoint/use case или типизированный режим с allowlist; обработчик не принимает произвольные клиентские флаги ослабления.

Like может обучать вкус цвета/категории/стиля, но не соответствие размера. Метрики discovery отделяются от первых 20 exact-fit карточек, размера покрытия и количества валидных образов. Сохранённый discovery-товар сохраняет статус проверки; позднее обновление карточки не приписывает ему старые персональные причины.

## Конкретный путь к строгому покрытию

Нужна проверяемая связка: `source/feed_version` → `offer/variant_id` → модель/цвет → исходное значение → подписанная система или подписанные aliases этого же варианта → фактическое наличие этого варианта → дата наблюдения. Доказательство может быть публичной модельной карточкой/маркировкой или документацией источника; необязательно общий договор всего магазина. Область правила ограничивается доказанными моделями и вариантами, конфликтующее конкретное поле не перезаписывается.

Для сантиметрового подбора понадобится явно подтверждённая длина стопы пользователя, модельные мерки и отдельный честно названный результат подбора по меркам. Использовать среднюю таблицу бренда для перевода текущего EU/RU в сантиметры и затем обратно в неизвестный размер модели нельзя. Без этих данных этот путь не разблокирует текущие 9 452 SKU.

Новые критерии проверки discovery: неизвестный размер не попадает в strict выдачу; известный размер не совпадающего профиля не скрывается как подходящий; stale/unavailable/non-fashion/dubль исключаются; карточки и сохранённое показывают исходный статус; вкладка обратно в строгую ленту не сбрасывает viewed history; отдельные события не завышают strict acceptance. Для выпуска прежнего exact-fit ТЗ по-прежнему нужны реальные полные комплекты и ручная визуальная проверка.
